## 1. 진입과 화면 흐름

- 첫 진입은 **개인 / 멀티 선택 화면**. `/?room=CODE` 링크는 선택 화면을 건너뛰고 바로 그 방으로 간다.
- 새 라우트를 만들지 않는다. `/` 안의 화면 상태로 둔다 (프리렌더 셸 유지).

```
선택 → 로비(공개 방 목록 · 방 만들기 · 코드 입력) → 대기실 → 게임 → 결과
      → 방장이 다음 게임 선택 → 대기실(전원 준비 해제) → …
```

### 멀티 게임 화면

| 항목 | 내용 |
|---|---|
| 배치 | 가운데에 개인 플레이와 같은 보드·키보드. 상대 패널은 **좌·우 여백에 2개씩 세로로**(□나□ / □나□), 위·아래에는 두지 않는다 (2026-11-01 캔버스 댓글로 결정) |
| 모바일 | 여백이 없으므로 패널을 **보드 위 가로 띠**로 내린다 (넘치면 가로 스크롤) |
| 패널 내용 | 이름, 상태(제안함 / 풀이 중 / 완료 n위 / 탈락 / 접속 끊김) |
| 협동 패널 | 그 사람이 제안 중인 단어 (실시간) |
| 경쟁 패널 | 같은 격자에서 제출한 행의 **색만** (자모 숨김). 입력 중인 행은 비움 |

### 채팅과 재촉

채팅은 2026-11-14 사용자 요구로 넣었다(2026-11-01 결정은 "v1 없음"이었다).

- 참가자(자리가 있고 게임 중 나가지 않은 사람)는 대기실·게임 중·결과 어디서나 방 전원에게 보낸다. 경쟁 중에도 막지 않는다.
- 본문은 앞뒤 공백을 지운 1~100자(코드포인트). 줄바꿈·탭은 공백으로 바꾸고 나머지 제어문자와 보이지 않는 서식 문자(제로폭 공백·양방향 제어 등, 이모지용 ZWJ는 제외)는 지운 뒤 잰다. 보이는 글자가 하나도 없으면 거절한다. 사람마다 5초 안에 5개까지, 넘으면 서버가 `cooldown`으로 거절하고 화면에 짧게 알린다.
- **저장하지 않는다.** 서버는 DO 메모리에 최근 30개만 들고(링버퍼) `RoomState`와 `storage.put`에는 넣지 않는다: 채팅이 SQLite 쓰기 한도를 먹지 않게 한다. DO가 쉬었다 깨면 기록은 사라지고 그래도 된다. 접속·재접속 때 메모리에 남은 기록을 받는다. 브라우저에도 저장하지 않고 화면은 최근 100줄만 메모리에 둔다.
- 스냅샷에 싣지 않고 별도 메시지로 방 전원에게 방송한다. 본문은 텍스트로만 그린다(HTML 해석 없음).
- 화면: 데스크톱 대기실은 참가자 카드 오른쪽 패널(340px), 모바일 대기실은 하단 바의 `채팅` 버튼, 게임 중은 머리 줄의 채팅 아이콘 버튼, 결과는 모달 안 `채팅` 버튼. 모바일은 하단 시트, 데스크톱 게임·결과는 오른쪽 서랍이다. 안 읽은 수는 배지(숫자 글자)와 시트 안 구분선으로 같은 값을 보인다. 열린 채팅의 입력칸에서 친 키는 게임 입력에 들어가지 않는다. 협동 투표 중에도 채팅이 열리고 투표 시트 위에 쌓인다(투표 시트 안 `채팅` 버튼). 화면이 바뀌면(대기실로 돌아가는 등) 열린 채팅은 닫히고 쓰던 글은 남는다. 좁은 화면에서는 시트를 열어도 입력칸에 포커스를 주지 않아 키보드가 올라오지 않는다. 시트가 열려 있는 동안 게임이 끝나면 결과 모달은 시트를 닫은 뒤에 뜬다(가려진 모달이 포커스·Esc·Enter를 가로채지 않게). 640px 넘는 서랍도 소프트 키보드 위에 붙는다. 스크린리더는 남이 보낸 메시지만 별도 영역으로 읽고(입퇴장 줄은 토스트가 읽고, 내 글은 읽지 않는다) 로그 자체는 라이브가 아니다.
- 입장·퇴장·방장 변경은 서버가 만들지 않는다. 클라이언트가 기존 스냅샷 비교 토스트 경로에서 회색 시스템 줄로 함께 넣는다(이 브라우저에만 있다). 게임 결과 등은 넣지 않는다.
- 비범위: 기록 저장, 신고, 차단, 이모지 반응, 멘션. 강퇴가 없는 점은 그대로다(§9).
- 수신 메시지 예산: 채팅 한 줄은 수신 WS 메시지 1건(요청 1/20)이다. 사람당 상한이 초당 1건이라 5인이 10분 내내 한도까지 보내도 3,000건(약 150요청)이고, 송신(방송)은 과금이 없다. `MULTIPLAYER_TASKS.md` R28.
- 대기실에 **"재촉" 버튼**: 방장 화면 전체 알림 레이어(소리·흔들림·배지, 닫을 때까지 유지), 1인당 30초 쿨다운. 2026-11-01 결정. 언제나 가능한 "나가기".
- 방장 잠수는 시스템이 풀지 않는다 (자동 방장 교체·자동 시작 없음). 사용자 결정: 보통 독촉하다 안 되면 방을 나가 다른 방을 찾는다.

### localStorage 새 키

| 저장소 | 키 | 값 |
|---|---|---|
| localStorage | `nkordle:mp-session` | 임시 계정 `{ token, name, exp }` (이것 하나뿐, 2026-11-01 사용자 결정) |

sessionStorage·BroadcastChannel·쿠키는 쓰지 않는다. 새로고침·재접속·같은 브라우저의 새 탭은 토큰의 같은 `uid`로 같은 자리에 복귀한다(끊김 60초 규칙은 그대로). 기존 키 형식은 건드리지 않는다. 자세한 원칙은 §7 "브라우저 저장 최소화와 임시 계정".

### 준비

- **방장을 뺀 전원이 준비 완료여야 시작 버튼이 켜진다.** 방장 화면에 인원별 준비 상태와 "n명 대기 중".
- 방장이 **규칙에 영향 주는 설정**을 바꾸면 전원 준비 해제.
- 게임이 끝나 다음 게임을 고를 때도 전원 준비 해제 후 같은 절차.
- 접속 끊긴 사람은 준비 해제로 본다. 신규 입장자는 본인만 미준비.

### 진행 중 방과 입장

- 진행 중 방은 목록에 "진행 중" 태그로 보이되 입장 불가. 관전 없음.
- 게임과 게임 사이(방장이 다음 게임 고르는 동안)에만 새 참가 가능.
- 등반은 스테이지가 이어지는 동안 **한 게임**으로 취급한다.

### 방장 권한

설정, 시작, 다음 게임 선택, 협동의 제안·투표 마감, 협동의 포기, 경쟁에서 끊긴 사람 강제 탈락(§5), 방장 넘기기.

**방장 넘기기** [사용자 결정 2026-11-14]: 방장이 대기실·결과에서 접속 중인 다른 참가자 한 명에게 방장을 넘긴다. 게임 중에는 넘길 수 없고, 끊긴 사람·자기 자신·방에 없는 사람에게도 못 넘긴다. 넘기면 새 방장의 준비는 풀리고(방장은 준비하지 않는다) 옛 방장은 준비 안 함 상태의 일반 참가자가 된다. 다른 참가자의 준비는 유지한다. 방 안 토스트와 로비 목록의 방장 이름은 자동 승계와 같은 경로로 바뀐다. 되받기·연속 넘기기에 제한은 없다.

## 3. 게임 설정

방장이 정하고 매 게임마다 바꿀 수 있다. 결과 화면에 "같은 설정으로 한 판 더" 버튼.

| 설정 | 값 | 구분 |
|---|---|---|
| 종류 | 협동 / 경쟁 | 사용자 결정 |
| 게임 | **단판** / **등반** | 사용자 결정 |
| 시작 길이 | 5~12 또는 랜덤 | 기본값(제안) |
| 시도 횟수 | 4~10, 기본 6 | 기본값(제안) |
| 하드모드 | 켬/끔 | 기본값(제안) |
| 힌트 | 허용 여부 | 사용자 결정 |
| 제한 시간 | 켬/끔, 기본 끔 (2026-11-05 구현에서 기본값을 끔으로) | 켬/끔: 사용자 결정 / 수치: 기본값(제안) |
| 협동 선택 방식 | 투표 / 돌림판 | 사용자 결정 |

### 게임 두 가지만

- **단판**: 한 단어.
- **등반**: 시작 길이에서 12자까지 한 자모씩 올라간다. 12자 완주가 결승선이라 목표 스테이지 수 설정이 없다.
- 개인 모드를 그대로 쓰지 않는다. **연속 클리어**는 난이도 상승이 없어 멀티에서 긴장을 만들지 못해 제외. **데일리 2종**은 모두가 그날 정답을 알게 되므로 제외.

### 제한 시간 (수치는 기본값(제안))

| 게임 | 시간 |
|---|---|
| 등반 | 1스테이지 180초, 스테이지마다 −15초, 하한 60초 |
| 단판 | 라운드 상한 180초 |

만료 = 그 판/스테이지 실패.

### 정답 풀

멀티는 상수 하나 **t=3** (데일리급 깨끗한 풀). 개인용 allowlist인 `POOL_THRESHOLD`와 무관한 별도 상수. D1 `pool` t=3 행은 이미 있으므로 재임포트가 필요 없다.

## 4. 협동 규칙

### 한 행의 흐름: 제안 → 선택 → 판정

1. 각자 자기 입력 행에 단어를 친다 (다른 사람 패널에 실시간 표시). Enter로 제안 확정.
2. 서버가 사전·하드모드를 검사한다. 마감 전까지 수정하거나 **제안 취소**로 거둘 수 있다.
3. 접속 중인 전원이 제안하거나 **패스**하거나 방장이 "마감"하면 (제안 ≥1) 선택 단계. 같은 단어 제안은 하나로 합친다. **제안이 하나뿐이면 바로 제출.**
4. 선택된 단어가 공유 보드에 들어가고 다음 행 제안으로.

### 선택 방식

| 방식 | 규칙 |
|---|---|
| 투표 | 자기 제안에도 찍을 수 있음 [사용자 결정 2026-11-14]. 투표 단계는 **20초**. 접속 중 전원이 찍거나 방장이 마감하거나 20초가 지나면 집계. 동률은 돌림판 |
| 돌림판 | 서버가 먼저 결과를 정하고, 클라이언트는 제안 사이를 돌다 멈추는 연출 (약 1.5초) |

2인 방에서 각자 자기 제안을 찍으면 1:1 동률 → 돌림판이 된다.

### 투표 제한 시간 [사용자 결정 2026-11-14]

- 투표 단계에 들어가는 순간 20초(`VOTE_MS`)를 센다. 방 제한 시간이 꺼져 있어도 적용한다. 만료는 방장 마감과 같다: 그 시점의 표로 집계하고, 아무도 안 찍었으면 전 후보 동률이라 돌림판이다.
- 나간 사람 때문에 후보가 줄어 투표 단계를 다시 꾸려도 마감은 처음 그대로다(20초로 늘어나지 않는다). 후보가 하나로 줄면 바로 제출한다.
- 만료 시점에 접속 중인 투표권자가 없으면(전원이 끊김 유예 중) 집계하지 않고 마감만 20초 뒤로 민다. 아무도 없는 사이에 한 행이 소진되지 않게 한다.
- 방 제한 시간(공유 보드 마감)이 먼저거나 같으면 그 판이 시간 초과로 끝나고 투표는 집계하지 않는다.
- 이 기능이 생기기 전에 저장된 투표 단계는 마감 없이 기다린다(전원 투표·방장 마감으로만 끝난다). 다음 행부터 마감이 걸린다.
- 제안 단계에는 시간 제한이 없다.
- 화면: 투표는 게임 화면 위의 모달 시트로 열리고 남은 시간(초 숫자·줄어드는 막대, 마지막 5초는 아이콘·테두리·`곧 마감`)과 `투표 k/m명`을 보인다. 득표수는 실시간이고 누가 어디에 찍었는지는 보이지 않는다. 시트 동작은 작업 문서 S4-V.

### 제안 취소 [사용자 결정 2026-11-14, 이전 결정 "철회 없음"을 뒤집음]

- 제안 단계에서 내가 확정한 제안을 거둘 수 있다. 거두면 제안이 사라지고 내 초안은 거둔 단어로 남아, 남들에게는 다시 입력 중으로 보인다. 다시 고쳐 제안하거나 패스할 수 있다.
- 제안하지 않은 상태(패스 포함)와 투표 단계에서는 거절한다. 접속 중 전원이 제안하면 곧바로 선택 단계로 넘어가므로, 취소는 남이 아직 제안 중일 때만 가능하다.

### 패스

제안 단계에서 **이번 행만** 제안하지 않고 넘어가는 버튼이다 [사용자 결정 2026-11-11].

- 접속 중인 참가자가 제안하지 않은 상태에서 누를 수 있다. 제안과 똑같이 "다 냈다"로 세어, 접속 중 전원이 제안하거나 패스하면 기다리지 않고 선택 단계로 간다(방장 마감은 그대로 제안 ≥1).
- 마감 전에 제안하면 패스가 풀린다. "패스 취소"로도 푼다. 제안한 사람은 패스할 수 없고, 제안을 취소하면 패스할 수 있다. 다음 행은 패스가 모두 비워진 채 시작한다.
- 패스한 사람도 선택 단계에서 다른 사람과 같이 투표하고, 그 표는 기다린다(자기 제안이 없을 뿐이다).
- **마지막 사람 규칙**: 제안이 하나도 없는데 다른 접속자가 전부 패스했다면 마지막 사람은 패스할 수 없다("제안이 하나도 없어 패스할 수 없습니다"). 접속이 끊기거나 나가서 남은 접속자가 전부 패스뿐이고 제안이 0건이 되면 패스를 모두 풀고 "모두 패스해서 다시 제안합니다"를 알린다(진행이 멈추지 않게).
- 패스한 사람은 이번 행에 입력할 것이 없으므로 무입력 경고(§6) 대상이 아니다.

### 협동 힌트: 투표 [사용자 결정 2026-11-11, 경쟁은 그대로]

- 힌트 허용 시 판당 1회(등반은 등반 전체에서 1회). **힌트 버튼은 투표를 연다.** 게임은 멈추지 않고, 요청한 사람이 찬성 1표다. 다른 사람은 보드 위 막대에서 찬성·반대를 고른다(집계 전까지 바꿀 수 있다).
- 투표권자는 평가 시점의 **접속 중인 참가자**다. 찬성이 투표권자의 과반이면 즉시 통과(2인 방은 둘 다), 반대가 절반 이상이라 남은 표가 모두 찬성이어도 과반이 안 되면 즉시 부결, 30초 안에 결론이 안 나도 부결(서버 알람). 투표하지 않은 사람은 찬성으로 세지 않는다.
- 접속 인원이 바뀌면(끊김·나감·재접속) 투표권자를 다시 세어 다시 판정한다. 요청자 본인의 표도 접속 중일 때만 센다.
- 부결되면 힌트는 그대로 미사용이고 다시 요청할 수 있다. 부결 직후 10초는 재요청을 막는다(반복 요청 방지, 기본값(제안)).
- 통과하면 기존과 같은 힌트(`pickHint` 규칙)가 **통과 시점의 보드**에 들어가고 쓴 사람은 요청자다.
- 투표를 접는 경우: 판이 끝날 때, 등반이 다음 스테이지로 넘어갈 때, 요청자가 나갈 때. 같은 스테이지에서 행이 제출되는 것은 접는 이유가 아니다(힌트는 최신 보드에 들어간다).
- 투표 중에는 힌트 버튼이 "힌트 투표 중"으로 잠긴다.

### 진행 표시

- 제안 단계의 진행은 하단 "제안 k/n" 줄 대신 **상대 패널**로 보인다. 제안을 확정한 사람의 패널은 완료 패널과 같은 2px `--sel-line` 테두리와 "제안함" 칩, 패스한 사람은 테두리 없이 중립색 "패스" 칩. 내 상태는 보드 아래 한 칸의 칩으로 같은 말을 쓴다. 스크린 리더용 상태(제안 k/n, 패스 수)는 그대로 읽힌다.
- 선택 단계의 화면은 그대로다.

### 그 밖

- 포기는 방장.
- 협동 등반: 공유 보드로 스테이지를 이어가고, 실패 또는 12자 완주로 끝난다.
- 끊긴 사람은 제안·투표 집계에서 뺀다 (탈락 없음).

## 5. 경쟁 규칙

- 같은 정답, 각자 보드, 같은 시도 횟수. 힌트 허용 시 1인 1회. 포기는 본인만 탈락.
- **단판**: 전원이 끝날 때까지 (정답·실패·포기·제한 시간 만료). 순위 = 정답자(시도 수 → 완료 시각) 다음 미정답자(아래 지표).
- **경쟁 등반 = 독립 등반.** 같은 단어 순서를 각자 자기 속도로 오른다.
  - 스테이지 실패는 그 자리에서 등반 종료 (높이 확정).
  - 첫 완주자(12자 클리어)가 나오면 1위 확정 + **유예 60초**. 유예 중 완주하면 완주 순서대로, 유예가 끝나면 나머지를 아래 지표로 고정.
  - 전원 실패해도 종료.

### 순위 지표 (서버 계산)

순서대로 비교한다. 단판은 1번만 빠진다.

| 순서 | 지표 | 정의 |
|---|---|---|
| 1 | 등반 높이 | 클리어한 스테이지 수 |
| 2 | 정답 자모 수 | 현재 스테이지에서 초록으로 확정된 **자리** 수 (행 합집합) |
| 3 | 불완전 정답 자모 수 | 노랑으로 확인된 **자모 종류** 수 |
| 4 | 시도 수 | 적은 쪽이 위 |
| 5 | 공동 | |

### 접속 끊김과 통계

- 이미 끝난 사람은 남은 사람의 진행(색만)과 현재 순위를 본다.
- 접속 끊김 60초 넘으면 자동 탈락 (그래야 "전원 종료"가 성립). 방장은 그 전에도 강제 탈락 가능.
- 멀티 결과는 개인 통계(`stats:<mode>`)에 기록하지 않는다 (기본값(제안)).

## 6. 제한 시간과 무입력

- 서버는 플레이어별(협동은 방별) **마감 시각만** 저장한다. 제출 시 검사하고, 가장 이른 마감에 DO 알람 하나를 건다. 클라이언트는 남은 시간을 받아 카운트다운.
- 무입력 60초(기본값(제안))면 그 사람에게 "진행 중입니다" 경고 모달. 닫고 입력하면 그대로 이어진다. **자동 포기·강제 퇴장 없음.** 입력할 것이 있는 사람만 대상이다(협동 제안 단계에서는 제안도 패스도 안 한 사람).
- 끝까지 반응 없으면 제한 시간 만료가 실패로 처리한다. 제한 시간을 끈 방에서는 경고만 뜨고 기다린다.

## 7. 아키텍처

### 구조

| 구성 | 역할 |
|---|---|
| `Room` Durable Object (방 하나 = DO 하나) | 정답·참가자·보드·판정 보유. WebSocket Hibernation API, 소켓 첨부에 playerId |
| `Lobby` DO (싱글턴) | 공개 방 목록. RPC `list`·`upsert`·`remove`, 목록 구독 WebSocket(`fetch`) |

- D1 폴링 대안은 제외했다: "PK 한 행만" 규칙(AGENTS)과 충돌하고 협동 입력 동기화가 안 된다.
- **정답은 DO에만 있다.** 멀티에서는 HMAC 토큰을 쓰지 않는다. `KORDLE_SECRET`과 무관.
- 상태 전송은 변경 때마다 **개인화된 전체 스냅샷** (경쟁은 남의 보드를 색만으로 가공). 방 상태가 작아 (5명 × 10행 × 12자) 패치보다 단순하고 재접속에 강하다.

### 브라우저 저장 최소화와 임시 계정 (사용자 결정 2026-11-01)

신원은 **서버가 발급하는 임시 계정 토큰**으로 한다. 이전 안(sessionStorage `secret` + BroadcastChannel 전달, localStorage `mp-name`)은 폐기했다.

**저장**
- 게임 데이터(추측 행, 초안, 투표, 결과, 상대 정보)는 **브라우저에 저장하지 않는다.** 메모리에만 있고, 새로고침·재접속은 서버 스냅샷으로 전부 다시 그린다. 쿠키는 쓰지 않는다.
- 허용하는 클라이언트 저장은 둘뿐이다. ① localStorage `nkordle:mp-session` 한 키 = `{ token, name, exp }`. ② 현재 방 코드는 URL `?room=CODE`(변경 제안 P6).
- 개인 플레이의 기존 키·형식은 건드리지 않는다. "재촉 소리" 같은 멀티 전용 설정은 저장하지 않고 세션 동안만 유지한다(기본 켬).

**토큰**
- 형식 `mp1.<uid>.<name>.<iat>.<sig>`. `uid`는 16바이트 난수의 base64url(22자), `name`은 닉네임(원문 5~12자, 앞뒤 공백 제거, NFC 정규화)의 base64url, `iat`는 발급 시각(초, 서버), `sig`는 HMAC-SHA256(`KORDLE_SECRET`, `"mp1." + uid + "." + name + "." + iat`)의 base64url 앞 32자.
- 개인 모드 정답 토큰(`n.t.idx`)과 **별개 종류**다. `mp1.` 접두어로 도메인을 나누고, 기존 토큰 형식과 검증 코드는 건드리지 않는다. 서버 저장 없음(무상태), D1·DO 쓰기 없음.
- **만료는 마지막 사용 후 24시간(슬라이딩).** 서버는 `now - iat ≤ 24h`이면 유효로 보고, 유효한 `hello`마다 `iat = now`로 재발급해 첫 `snap`에 `session: { token, exp }`(`exp = iat + 24h`)로 돌려준다. 시각은 서버 기준이고 클라이언트 시계는 믿지 않는다.
- **발급**: 멀티 첫 진입 시 S0에서 닉네임을 입력받고, 방 만들기·입장 때 WS `hello { token?, name }`. 토큰이 없거나 만료·서명 불일치면 서버가 새 `uid`로 발급한다. 서명 불일치도 4005 등으로 거절하지 않고 새로 발급한다(오래된 토큰 때문에 못 들어오는 일을 막기 위해. 만료는 정상 경로). 이름을 바꾸면 같은 `uid`로 새 이름에 서명해 재발급한다. `POST /api/room`(방 생성)도 같은 토큰을 받고, 없으면 발급해 응답에 `session`을 넣는다.
- 클라이언트는 부팅 시 `exp < now`면 키를 지우고 닉네임을 다시 묻는다. 서버가 준 `session`의 `uid`가 바뀌면 키를 덮어쓴다. "나가기"는 세션을 지우지 않는다(24시간 안 재진입은 같은 사람). 설정 모달의 "임시 계정 지우기"는 키를 지우고 S1로 보낸다.

**방 안 신원과 규칙**
- Room DO의 플레이어 키는 `uid`다. 공개 `pid`는 그대로 따로 두고, 스냅샷에는 `uid`·토큰을 절대 넣지 않는다.
- 같은 브라우저의 모든 탭은 localStorage를 공유해 같은 계정이다. 같은 `uid`의 새 소켓이 오면 기존 소켓을 4000으로 닫고 "다른 탭에서 접속했습니다"를 보인다(자리 넘겨받기).
- 끊김 60초 → 탈락 규칙은 유지한다(승부 무결성). 같은 `uid`는 방이 살아 있는 동안 자동 재입장한다: 대기 중이면 자기 자리(준비 상태는 해제), 진행 중이고 60초 안이면 자기 자리로 복귀, 60초가 지나 탈락했으면 관전 없이 결과 화면부터 합류(다음 판부터 참가). 방장 승계는 기존 규칙.
- 기본값(제안): 60초 안의 끊김은 자리를 유지하고 시작을 막지 않는다. 시작 시점에 끊긴 사람이 있으면 방장 화면의 시작 버튼이 "{이름} 내보내고 시작"으로 바뀐다.
- 공용 PC에서 24시간 안에 다른 사람이 같은 자리를 쓸 수 있다. 사내 소수 사용을 전제로 허용한다.

### 기존 모듈 재사용

`dict.ts`의 `isValidJamo`·`answerCount`·`answerAt`(t=3), `judge.ts`, `hard.ts`. 이 모듈들은 타입 import뿐이라 DO에서 그대로 쓸 수 있다. D1 읽기는 제출당 `valid` 1행이고, 정답은 시작 때 길이마다 2행(`pool_meta`+`pool`)을 읽는다(등반은 최대 16행).

**DO 코드에서는 `$lib`·`$app` 별칭을 쓰지 않고 상대 경로만** 쓴다. wrangler 번들에서 별칭이 안 풀릴 수 있다.

### SvelteKit 연결

| 문제 | 해결 |
|---|---|
| adapter-cloudflare 7.2.9가 `wrangler.jsonc`의 `main`을 **자기 출력으로 덮어쓰고 지운다**(`main` 키가 아니라 그 경로의 **파일**을 지우고 템플릿으로 다시 쓴다) (`node_modules/@sveltejs/adapter-cloudflare/index.js` 58–59행(`main` 대입), 78행(rimraf), 117행(copy)) | 커스텀 엔트리 대신 **빌드 후처리 스크립트**가 `.svelte-kit/cloudflare/_worker.js` 끝에 `export { Room, Lobby } from "../../src/lib/server/mp/room"` 한 줄을 붙인다. `package.json`의 `build`를 `vite build && node scripts/…`로. CI는 `pnpm run build`를 거치지만 `package.json`의 `deploy`는 `vite build && wrangler deploy`라 `build` 스크립트를 **거치지 않는다**. `build`와 `deploy` 두 곳을 함께 고친다(`"deploy": "pnpm run build && wrangler deploy"`) |
| WebSocket 업그레이드 | 새 `src/hooks.server.ts`의 `handle`에서 `/ws/<code>` + Upgrade 헤더를 `platform.env.ROOM` 스텁으로 바로 넘긴다. `resolve`를 거치지 않으면 SvelteKit이 응답을 건드리지 않고, 어댑터 워커의 캐시 경로도 101 응답은 타지 않는 것을 코드로 확인했다 |
| 방 생성·목록 | `POST /api/room`, `GET /api/rooms`는 일반 SvelteKit 엔드포인트가 DO 스텁을 호출. 목록 화면은 `/ws-lobby` WebSocket으로 Lobby DO를 구독한다(2026-11 폴링 대체, 아래 "로비 목록 푸시") |

### 로비 목록 푸시

- 클라이언트는 로비 화면에 들어오면 `GET /api/rooms`로 한 번 채운 뒤 `/ws-lobby`(hooks가 Lobby DO `fetch`로 넘긴다)에 붙는다. 접속 직후 현재 목록 전체를 받고, 이후 `list()` 결과가 바뀔 때만 구독자 전부가 전체 목록을 받는다. 노출 규칙(심장박동·STALE·접속자 0 비노출)은 `list()`와 같은 `listRooms`를 쓴다.
- 같은 결과 판정은 `sameList`(코드별 비교, 순서와 `updatedAt` 제외)라 심장박동의 재정렬은 푸시를 만들지 않는다. 순서는 다음 실제 변경 때 갱신된다. 마지막으로 보낸 목록은 하이버네이션 뒤에도 비교되도록 저장소(`shown`)에 둔다.
- 시간만 지나 방이 빠지는 경우(STALE)는 구독자가 있을 때만 가장 이른 만료 시각(`nextStaleAt`)에 알람을 건다. 마지막 구독자가 나가면 알람을 지운다. 구독자가 없으면 푸시·알람 비용은 0이다.
- `ping`은 Room과 같은 `setWebSocketAutoResponse`로 DO를 깨우지 않고 `pong`을 돌려준다. 클라이언트는 25초(`HEARTBEAT_MS`)마다 보내고, 숨은 탭에서도 연결을 유지한다.
- 소켓이 끊기면 폴백으로 보이는 탭에서 `GET /api/rooms`를 15초(`LOBBY_FALLBACK_POLL_MS`)마다 부르고, 재연결은 3초에서 60초까지 지수 백오프로 보이는 탭에서만 시도한다. 탭이 다시 보이면 즉시 조회하고 재연결한다. 개발 서버(`pnpm dev`)는 WS가 안 되므로 목록 없이 안내만 보인다.
- 로비 소켓에는 서버 쪽 무응답 정리(Room의 `reapStale` 같은 것)를 두지 않았다. 숨은 탭의 ping이 1분 주기로 늦어질 수 있어 45초 기준을 쓰면 재접속이 반복되기 때문이다. 클라이언트가 pong이 75초 넘게 없으면 소켓을 버리고 폴백으로 넘어간다.

### wrangler.jsonc

- `durable_objects.bindings`: `ROOM`, `LOBBY`.
- `migrations: [{ tag: "v1", new_sqlite_classes: ["Room", "Lobby"] }]`. 무료 플랜은 SQLite 기반 DO만 가능.
- AGENTS의 "마이그레이션 없음"은 데이터 마이그레이션 얘기이고, 이것은 설정이다.
- 한도: 하루 요청 10만, WS 수신 메시지 20개당 1요청. 토이 규모에서 여유.

### 개발

- `vite dev`의 `getPlatformProxy`는 같은 워커의 DO를 못 띄울 가능성이 높다. **`pnpm dev`가 깨지면 안 된다.**
- `getPlatformProxy`는 빌드의 프리렌더에서도 돈다(kit `prerender.js`가 어댑터 `emulate()`를 호출). DO 바인딩이 이를 깨뜨리면 `pnpm dev`뿐 아니라 **`pnpm build`와 CI도 깨진다.** wrangler 4.129.1은 같은 워커의 DO 바인딩에 '로컬에서는 동작하지 않는다'는 경고만 찍고 진행하는 것을 코드로 확인했고, workerd도 기동을 거부하지 않았다(2026-11-05 스파이크: build·dev 정상, 경고만 "internal Durable Objects"·"no such Durable Object class is exported").
- 멀티 개발·검증은 `pnpm build && pnpm preview`(wrangler dev)로 한다. 2026-11-05 스파이크: 바인딩이 있어도 dev·build 정상이라 환경 분리는 필요 없다. dev는 WS 불가이고 WS 클라이언트가 붙었다 끊기면 Vite가 `ECONNRESET`으로 죽으므로(DO 무관) 멀티는 preview로만 검증한다.
- DO export는 빌드 후처리가 붙인다. `pnpm build` = `vite build && node scripts/postbuild-do.mjs`가 `_worker.js` 끝에 한 줄(멱등)을 더한다: `export { Room, Lobby } from "../../src/lib/server/mp/index.ts";`. 경로는 barrel `index.ts`(Room·Lobby 재export)를 거치고 `.ts` 확장자를 포함한다. `wrangler deploy --dry-run` 종료 0, 번들 `$lib/` 0 (2026-11-05 스파이크).
